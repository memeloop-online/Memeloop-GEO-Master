# Repository collaboration

This is a public repository.

- Read `docs/HANDOFF.md`, `docs/product-plan-v1.md`, and `docs/TODO.md` before implementation. Keep the product plan unchanged unless the product owner explicitly changes requirements. Track outstanding work in `docs/TODO.md` and completed work in `docs/WORKLOG.md`.
- User-provided research targets, customer/vendor identities, account identifiers, credentials, private endpoints, screenshots, and operational context are not public documentation material. Do not put them in tracked files, filenames, commit messages, PR bodies, comments, test fixtures, or logs.
- Record reusable product requirements in generic terms. Do not preserve identifiable competitor research in the repository, even in an evaluation appendix. Public upstream dependencies and their required license notices remain attributed.
- Before committing or publishing, inspect staged content and filenames for private context. A request to research a service does not authorize publishing its identity or account information.
- Preserve concurrent work. Never change branches, merge, rebase, commit, or push from a delegated task unless the coordinating agent explicitly assigns that operation.
- Prefer maintained open-source libraries for generic capabilities; do not build another rich-text editor, chat framework, or remote-desktop interaction stack. Assess licensing and integration before adding a dependency; implement only the product-specific adapter.
- Remote account login must use a maintained remote-desktop client/server stack. Remove legacy screenshot-polling and coordinate/key-action APIs rather than retaining them as a fallback. Do not add custom RFB, keyboard/composition, clipboard, or remote text-injection protocols. Thin tenant/session authorization, lifecycle, and library integration adapters remain product responsibilities; validate the actual library-backed UX instead of adding homegrown controls.
- AI conversation is the primary operating surface. Show the composer immediately and create the first conversation only on send. Detail pages inspect and fine-tune the same persisted data; do not make users complete setup forms before chatting or measuring arbitrary topics. Follow the UX consolidation backlog in `docs/ux-consolidation.md`.
- Product UI copy is for end users, not an engineering progress report. Describe the user's task, actual state, and available next action. Keep work-package IDs, implementation milestones, test/acceptance claims, API wiring notes, and roadmap narration in documentation, not interface labels or tooltips. Explain genuine limitations concisely without inventing capabilities or concealing failure. Use shared internationalization resources as they become available, rather than adding scattered brand or language literals.
