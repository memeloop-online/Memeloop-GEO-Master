# Browser runner (internal service)

Server-side Chromium runner for fixed creator platforms and the Kimi consumer-web measurement surface. Rust owns account authorization, durable attempts, leases, budgets, encryption at rest, and reconciliation. This process keeps browser contexts in memory and does not persist credentials.

Set `GEO_BROWSER_RUNNER_TOKEN` through a secret manager, then run `pnpm --dir packages/browser-runner start`. It binds `127.0.0.1:38080` by default. For container deployments, set `GEO_BROWSER_RUNNER_HOST=0.0.0.0` only inside a private network with ingress authentication/TLS and egress policy. Do not expose it publicly. A missing bearer token rejects startup. Proxy settings apply to the browser context itself; a failed specified proxy never falls back to direct traffic. Cookies and local storage are returned only by connection completion, to Rust for encryption.

The trusted deployment may set `GEO_BROWSER_CHANNEL` to `chromium`, `chrome`, or `msedge`. If it is absent, the runner uses Playwright's bundled Chromium pinned by this package's exact Playwright and lockfile versions; CI should leave the variable unset to retain that reproducible default. An explicit value is passed only as the matching allowlisted Playwright channel. `chrome` and `msedge` therefore select a browser installed and managed by the deployment; pin and roll out that installed browser version with the deployment image or host configuration because it is outside the npm lockfile. Invalid values reject runner construction before it can serve requests. Browser channel and executable path are never request fields, and arbitrary executable paths are not supported.

All routes require `Authorization: Bearer <internal token>`. JSON contract:

- `GET /v1/capabilities`: `{connectors:[{platform,placement_slot,connector_version,operations,verified:false}]}` describes the adapters actually loaded by this runner. Version discovery is not live publication/search verification and cannot enable a connector on its own.
- `POST /v1/sessions`: `{session_id,platform,storage_state?,proxy?}` → `{session_id,phase}`. Platform is one of `zhihu`, `baidu_creator`, `xiaohongshu`, `kimi`; proxy is `{server,username?,password?}`. Storage state is a Playwright JSON object, never a file path.
- `GET /v1/sessions/:id/snapshot`: `{phase,url,width,height,screenshot_base64,identity?}` (PNG). Screenshots can contain private account content and must be scoped to the owner in Rust.
- `POST /v1/sessions/:id/actions`: pixel `click` `{kind,x,y}`, focused-field `type` `{kind,text}`, allowlisted `key` `{kind,key}`, or `scroll` `{kind,delta_y}` → a fresh snapshot. This is only a user-controlled login surface, not a publication endpoint.
- `POST /v1/sessions/:id/complete`: `{identity:{platform_account_id,display_name,avatar_url?},storage_state}` only after adapter identity proof. Until then `409 login_required`; challenge pages give `409 challenge`. Completion disables user control while retaining the context for execution.
- `DELETE /v1/sessions/:id`: closes the in-memory browser context; this does not remove a persisted account.
- `POST /v1/executions`: `{execution_id,session_id,operation,payload}` with `operation` one of `publish`, `measure`, `lookup`. Returns `{execution_id,status,evidence,...}`. Results are `unsupported`, `login_required`, `challenge`, `unknown`, or `completed`. The same ID is deduplicated in-process, but Rust must keep the durable attempt ledger and reconcile unknowns before retry.

Idle sessions close after 15 minutes; completed execution cache entries expire after 5 minutes. Active executions are not reaped, and `DELETE` refuses an active session. Every execution has a 2-minute wall-clock deadline; expiry closes its context and returns `unknown`, never a retryable failure or success. These are memory-lifecycle limits, not durable idempotency guarantees: Rust must retain the execution ledger and explicitly close contexts when tasks end or accounts are revoked.

The current connector version is `live_unverified.source_derived.v1`. Own-account probes support the two API-backed creator identities through temporary pages in the same proxied browser context, and a third creator identity uses only its own dashboard control. These selectors are source-derived, not credential-smoke-tested. The first editor flow accepts `{title,body}` and returns `completed` only after an exact public title/body readback and an own-account article-list match; other outcomes are `unknown`. The moderated editor flow can submit the same typed payload but always returns `unknown` until public readback is independently verified. Other publication operations remain `unsupported`. Consumer-web measurement now selects the frozen model and search mode through the page, submits once, and captures its matching Connect JSON exchange. Only a correlated search block and completed answer can produce v2 evidence; default capability discovery still reports `verified:false` because real-account acceptance remains outstanding. Legacy injected candidate flows cannot produce completed official-search observations. A click, draft save, platform toast, or pending moderation state is never proof of publication. There is no arbitrary URL, selector, script, or anti-challenge API. Tests use synthetic pages; they do not publish to real accounts.

## Internal measurement evidence boundary

The server sends the frozen `target_id`, `account_id`, provider, model, surface, search mode, protocol and question-set versions, exact question, market, language, scheduled time and sample ordinal in its authenticated `measure` execution. A completed receipt must match its execution ID, use stage `official_search_observation`, have an occurrence timestamp and a matching nonfixture connector version, and contain exactly one structured official-search proof; unrelated evidence such as screenshot metadata may also be retained. Version labels alone do not establish provenance: Rust separately validates the trusted runner's execution stamp and all sample fields. The legacy v1 proof remains supported:

`{kind:"official_search_observation",schema_version:"geo.measure.official_search.v1",target_id,account_id,provider,model,surface,search_mode,protocol_version,question_set_version,question_sha256,market,language,scheduled_at,sample_ordinal,connector_version,provenance:"live",disposition:"observed"|"refused",raw_answer,citations,search_event:{kind:"official_search_event",source:"provider_search_event",provenance:"live",event_id,request_id,occurred_at}}`.

The question hash is SHA-256 of the exact UTF-8 question bytes. For v1, the provider event supplies request/event IDs and occurrence time. Connect v2 instead preserves actual chat/message/search-block IDs, event offset, locally observed time, and the matched request's model/question hash; it never invents a provider request ID. Both schemas require times inside the claimed execution and ingestion interval. See [the Connect observation contract](../../docs/connect-search-observation.md) for the v2 fields and byte-preserving CDP capture.

The receipt's connector version must match the evidence version, and all sample identity fields must match the frozen target. An `observed` answer retains credentials-free HTTP/HTTPS citation URLs including fragment anchors; a `refused` answer retains the refusal text and has no citations. Search-mode selection, an answer with links, a `search_verified` boolean, fixture pages, OAuth identity, or a fabricated event cannot substitute for an official search event. This contract relies on a trusted runner that independently establishes event provenance; it cannot make an untrusted runner truthful. Invalid completed receipts remain missing; explicit unsupported receipts remain unsupported. No external user can submit this evidence through the public API.

Run tests with `npm test` after `npx playwright install chromium`. In an environment with a preinstalled Chromium headless-shell, `GEO_TEST_CHROMIUM_PATH` can point tests to that binary. The container image already includes the matching browser.
