# 正文自动事实修正

本契约细化既有第一层 fan-out，不修改冻结产品规格。当前验证状态见 `WORKLOG.md`。

## 状态与操作

正文独立检查发现有效的阻断结论时，分支进入 `needs_repair`，继续计入未完成分母，不提前封存或进入分发。既有 MJS 工作流负责生成、检查和修正的提示与模型调用；Rust 从同项目的持久记录读取正文、检查结论和原始证据，领取步骤并保存结果。修正模型不决定是否就绪。

当前宿主契约为 `geo.hostops.v21`，共 51 项操作。检查使用 `content.check.begin.v1`／`content.check.finish.v1`，修正使用 `content.repair.begin.v1`／`content.repair.finish.v1`，不保留旧的单步操作。Begin 接收执行和清单项引用，返回当前结果或已领取的持久令牌与输入；Finish 接收同一引用、令牌及 `completed { text }`／`unavailable`／`invalid`。生成、检查和修正共用 `ContentModelOutcome`。运行时、调用方与两份 bundle 必须一起更新并重新计算摘要。

一次修正成功后追加新正文版本，保留原版本、原检查和完全相同的证据引用及摘录，回到 `drafted` 重新独立检查。每个清单项最多完成两轮自动修正；第二轮后检查仍不通过则 `blocked`。`automatic_repair_count` 是持久计数，不从正文版本号推导，手工编辑不重置它。检查通过才成为 `ready`。

资料不足、用途已不允许公开、无效检查输出等普通阻断不会进入修正。修正输出无效同样终止该分支；临时模型故障释放步骤租约后可重试，不算已完成一轮修正。两轮限制针对已持久化的修正版本，不代表最多发生两次上游请求。

## 恢复与并发

- 检查及修正租约绑定当前正文版本；并发手工编辑使旧输出无法提交。
- PostgreSQL 在同一事务中追加正文/检查并更新执行状态；内存模式沿用同一领域转换。
- 重入从持久状态继续，已保存的修正版本不再次生成。模型返回后、保存前崩溃仍可能重复模型请求，当前不声称模型调用恰好一次。
- 模型调用前后重新检查项目和公开证据资格；失效不产生可发布版本。
- `needs_repair` 属于未完成状态，支持取消，其他文档分支不因它停止；全部分支达到明确终态后才形成原有交接清单。
- 已完成步骤令牌重放只返回持久结果；未知、其他步骤或其他作用域的令牌不能提交。现有执行身份与冻结规划不重新创建。
- 宿主取消可能同时阻止清理调用；此时沿用既有租约到期恢复，不声称立即释放。普通模型失败可通过 Finish 释放租约。

## 页面与验证

P08 显示“待自动修正”、已完成轮数、当前原因及原有正文版本链接，并继续刷新状态；没有人工批准或放行操作。P09 沿用不可变版本和逐版本检查展示。

验收覆盖两轮后成功/耗尽、普通阻断不修正、失效来源、租约版本冲突、同项目隔离、重启后的计数与版本、无关分支及分母不变。Node 编排夹具不替代 Rust、PostgreSQL 或真实模型验证；正文就绪也不等于真实发布完成。
