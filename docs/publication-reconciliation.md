# 未知发布结果的自动查回

实施设计，尚未实现。细化冻结规格中的“发送后崩溃不盲目重发”，不代表真实渠道已验收。

## 当前缺口

`channel_execution_attempts` 为目标保留唯一发送尝试；`finish` 只保存一次结果。首次结果为未知后，不能通过覆盖该结果来补写成功。当前后台只执行从未尝试的目标，能力扫描只消费已保存的有效验证结果，两者都不是未知发布查回。

浏览器已有只读 `lookup` 操作，但支持范围取决于具体适配器。当前查回需要冻结标题、正文和候选公开 URL；发送超时不一定取得 URL，而且 Rust 只在已验证时保存 `public_url`。因此只加一个重试定时器无法解决未知结果。

## 实施顺序

1. 保存候选资产线索：把发送后观察到的 URL、提供方资产标识和事件关联作为**未验证线索**独立保存，不计成功、不赋予连接器发布能力。URL 必须符合适配器固定公开路径，不能携带账号令牌或任意跳转地址。
2. 建立独立查回账本：关联原 `attempt_id`、冻结版本/变体、账号、连接器版本，保存下一次查询时间、领取 token/到期时间、查询次数与稳定错误码；每次查询使用独立执行 ID，结果追加保存。过期租约只能重新查，不能重新发送。
3. 分页发现未知/缺少回执的发布尝试，原子领取查回任务，通过账号服务恢复加密 session 并重验身份，以同一指定出口调用只读 `lookup`。项目暂停停止新发布，不停止已发生副作用的只读查回。账号不可用则退避，绝不换账号认领资产。
4. 无候选 URL 时，仅使用已有、经验证的账号自有资产列表发现候选。核对冻结正文、标题和账号；多个相同候选、分页截断、访问失败或缺少发送关联均保留未知。列表中没找到不等于未发布，不能据此释放预算或重发。
5. 将可信查回结果投影为追加证据，独立记录观察时间和接收时间；在一个事务中幂等更新意图/命令的当前已知状态。原发送尝试、原未知证据和历史报告不修改。
6. 扩展正式及旧渠道报告输入，按原截止区分当时未知和后来验证。已保存周报保持不可变；现有显式更正可纳入迟到证据，自动更正排期需另行实现。

## 证据不能混用

- 存在一篇同账号、同正文的旧文章，仅证明资产存在，不证明本连接器成功执行了原发送。
- 升级发送结果或发布格式能力，需要真实发送与该资产的关联证据；缺少发送事件/提交后资产 ID/可信时间关联时，不制造一条 `Published` 回执。
- `project_saved_publication_verification` 当前仅接受原尝试的可信发布结果。新查回路径应有独立投影入口并核验发送关联，不能把原 `Unknown` 改成 `Verified` 来复用它。
- runner 实测来源标记、执行 ID、版本、账号归属、冻结内容摘要、时间窗口和引用资产必须相符；夹具、旧版无来源标记及适配器自报都不能升级。
- 公开读回使用无账号 Cookie 的浏览器上下文，同时保持指定出口；不允许代理失败后直连。

## 验证入口

分别覆盖发送前后崩溃、已取得 URL 但读回失败、完全无 URL、重复/延迟查询、进程重启、多副本领取、跨租户/账号、被暂停项目、重复正文歧义、不可访问资产、伪来源/版本/摘要、截止前未知与截止后更正。

最终端到端必须证明：原发送只发生一次；查回没有发布操作；结果晚到不覆写原报告；无法证明时仍显示未知。单独的浏览器查询夹具不能替代这些验收。
